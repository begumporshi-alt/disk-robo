## 1. Executive summary

**18 gaps found: 3 P0, 5 P1, 10 P2.** The three worst, in plain language:

1. **The cleanup exclusion checkbox is a lie.** You can uncheck candidates in the Cleanup list, the preview dims them and the Approve button says "Move *N* items to Trash" — but the executor trashes **every item in the plan**, including the ones you excluded. The spec's own journey J2 (`docs/02-ux.md:57`) promises "uncheck anything." For a safety-first product, the approval screen misrepresenting the action is the most serious possible defect.
2. **Duplicate cleanup only works for the first group.** `selectedURLs` resolves file IDs against only the first duplicate group, so selections made in any other group silently resolve to nothing — the action bar and confirm dialog undercount or never appear at all.
3. **"Trash contents" candidates free nothing but are reported as recovered.** `FileManager.trashItem` on an item already in `~/.Trash` succeeds as a no-op (verified empirically below), yet the outcome banner claims the bytes, the health score recalculates, and the audit log records "trashed."

And the biggest missing capability: **leftover app data (orphaned Library folders) can be seen in four places but removed through none** — the app's own origin story includes a 15 GB Docker leftover that had to be deleted by hand in Finder.

## 3. Gap list

### P0 — business-blocking

**G1 · Cleanup plan exclusion is cosmetic; executor trashes everything**
- Stage: Plan → Approve → Execute. Pattern: broken approval chain (the "missing chain link" between preview and executor).
- Missing: `executePendingPlan()` maps **all** `plan.items` (AppModel.swift:481) and `approvePendingPlan()` issues the token for **all** plan paths (AppModel.swift:473). `PlanPreviewSheet` filters `activeItems = plan.items.filter { !excludedIDs.contains($0.id) }` (CleanupScreen.swift:223) only for display; the Approve button even prints the filtered count ("Approve & Move \(activeItems.count) Items…", CleanupScreen.swift:321). The excluded set is `@State` in `CleanupScreen` and never reaches the model.
- Evidence: code paths above; no test asserts exclusion behavior (grep of Tests/ finds none); spec J2 mandates "uncheck anything" (docs/02-ux.md:57). In Deep mode this trashes orange items the mode description explicitly says "require individual selection" (CleanupScreen.swift:124).
- Fix sketch: pass the exclusion set (or a filtered item list) into `buildPlan`/`approvePendingPlan`/`executePendingPlan` — simplest: `buildPlan` takes `excluding: Set<String>` and drops them from `plan.items` so token, preview, and executor all agree. Add a test that an excluded candidate is not in the executed set.

**G2 · Duplicates: selections outside the first group are silently un-actionable**
- Stage: Review → select → Execute.
- Missing: `selectedURLs` (DuplicatesScreen.swift:11-15) does `model.duplicates.first { $0.id.hashValue != 0 }?.files.first { $0.id == id }` — it looks up every selected file ID inside **one** group (effectively the first). File IDs from any other group resolve to nil and are dropped.
- Effect: select copies in group 2+ → `selectedURLs` is empty → the footer/action bar never appears (`if !selectedURLs.isEmpty`); mixed selections trash only the first group's files and the confirm dialog shows the wrong count.
- Fix sketch: `selections` should key by group and resolve within that group: `for (groupID, ids) in selections { let g = model.duplicates.first { $0.id == groupID }; urls += ids.compactMap { id in g?.files.first { $0.id == id }?.url } }`. Add a multi-group test.

**G3 · Leftover app data: visible everywhere, removable nowhere** *(top P1 — proven real-world case)*
- Stage: Analyze → Review → Execute (leftovers). Pattern: read-only gap + dead-end recommendation.
- Missing: a removal path. Evidence chain: (a) CleanupEngine never produces `.leftover` candidates — `makeCandidate` has no `.leftover` case (CleanupEngine.swift:110-179, hits `default: return nil`); (b) the Uninstaller picker lists only installed apps (UninstallerScreen.swift:377-389) and its Leftovers card is view-only `prefix(6)` rows with no selection (UninstallerScreen.swift:443-455); (c) AppsScreen's AppDetail for leftovers says "Review before removing" but offers no action; (d) Radar's leftovers finding recommends "Review in Uninstaller → Leftovers" (RadarEngines.swift:155) — a dead end.
- Real-world proof: the user's own machine had `~/Library/Containers/com.docker.docker` (~15 GB orphaned Docker data, documented in project memory, 2026-09-06); removal had to be done manually in Finder. `AppFootprint.components` already carries the exact path/size a removal flow needs (AppAnalyzer.swift:169-175) — only the write chain is missing.
- Fix sketch: make the Uninstaller's Leftovers card interactive (select → trash via `trashUserSelected`, which already passes SafetyEngine for non-Group-Container paths), and/or surface leftovers as orange `.leftover` candidates from AppAnalyzer results. New write chain → follow the [[frontend-flow-to-atomic-rpc]] pattern (one action, one validated pipeline).

### P1 — workaround exists

**G4 · Plans built from Overview / Target sheet / Assistant are never shown**
- Stage: cross-screen chain link. `goClean` (OverviewScreen.swift:202-206), `TargetCleanupSheet` (OverviewScreen.swift:426-433), and assistant `.buildPlan` (AppModel.swift:361-362) all set `pendingPlan` and navigate to Cleanup — but the preview sheet opens only on the local Build Plan button (`showPreview` @State, CleanupScreen.swift:104-106), and the mode picker defaults to Quick. The user lands on a screen showing a Quick picker and must re-pick the mode and re-click Build Plan; the built plan is silently overwritten.
- Fix sketch: have `CleanupScreen` observe `model.pendingPlan` (e.g. `.onChange` + a "plan ready" flag on the model) and auto-present the sheet; or move plan presentation into AppModel as sheet state.

**G5 · "Trash contents" candidates report false recovery**
- Stage: Execute → Verify. `~/.Trash` children are green candidates (CleanupEngine.swift:71,110-134), counted in RecoverableCard's "Safely cleanable now" and Quick plans. Empirical test (2026-09-06): `FileManager.trashItem` on an already-trashed path **returns success and moves nothing**. So the OutcomeBanner claims "Recovered X GB" including Trash bytes, health/insights/radar recompute on phantom recovery, and the audit log records "trashed" — which also pollutes RepeatOffender statistics (RepeatOffenderEngine keys on `result == "trashed"`).
- Fix sketch: either drop `.trash` candidates from plans (keep the Radar trashBuildup finding, which correctly says "empty in Finder"), or execute them as an explicit "empty Trash contents" flow with a distinct outcome type that does not count as recovered. If kept, apply [[denormalized-balance-drift]]-style discipline: anything derived from the audit log must be recomputed from real freed bytes.

**G6 · No restore path after cleanup (and the Trash location is discarded)**
- Stage: Restore. `trashItem`'s `resultingURL` (where the item landed in `~/.Trash`) is discarded (TrashExecutor.swift:123-124); the audit log stores only the original path. No screen offers restore. UI copy promises "You can restore items from the Trash" (CleanupScreen.swift:256, FilesScreen.swift:89) — but Finder's Put Back is generally unavailable for programmatically trashed items, so the practical path is manually dragging out of Trash using the path shown in the Cleanup Log.
- Fix sketch (minimal): record `resultingURL` in `CleanupActionRecord` and add a "Reveal in Trash" action on log rows. (In-app one-click restore would additionally need `NSWorkspace`/`NSFileManager` move-back + existence checks.) Severity needs user confirmation — see §5.

**G7 · Uninstall doesn't refresh the apps list**
- Stage: Execute → Record. `applyTrashOutcome` prunes scan tree/candidates/duplicates but not `apps`/`leftovers` (AppModel.swift:510-543), and the Uninstaller never re-analyzes after trashing. The just-uninstalled app keeps appearing in the picker, Apps screen, and Overview Top Consumers until a manual "Re-analyze".
- Fix sketch: after a trash outcome that intersects `apps`/`leftovers` paths, trigger `analyzeApps()` (or prune those arrays the same way duplicates are pruned).

**G8 · User's free-space warning threshold ignored by Radar and Forecast**
- Stage: Learn/Alert. `freeSpaceWarningGB` is configurable in Settings (SettingsScreen.swift:100-106) and honored by notifications (AppModel.swift:316), but `recomputeRadar` calls `RadarEngine.analyze` and `ForecastEngine.forecast` without the threshold (AppModel.swift:322-332), so both use their hardcoded 20 GB defaults; GrowthTracker's label also hardcodes "20 GB" (SmartToolsScreens.swift:279). A user who sets the warning to 50 GB gets notifications at 50 GB but no Radar finding until 20 GB.
- Fix sketch: thread `settings.freeSpaceWarningGB` into both engine calls and the GrowthTracker label.

### P2 — friction / unreachable-but-harmless

**G9 · Unreachable enum values: `CandidateKind.duplicate`, `.leftover`** — no producer exists (CleanupEngine.swift:110-179); PlanPreviewSheet's "Duplicates"/"App leftovers" group titles (CleanupScreen.swift:271-292) can never render. Remove them or build their producers (see G3).
**G10 · `AppSettings.autoSnapshot` has no UI** — engine-honored (AppModel.swift:302), no toggle in SettingsScreen. Users can't turn snapshots off despite the setting existing.
**G11 · Scan failure message invisible** — `.failed(String)`'s message is never rendered; only a red status dot (OverviewScreen.swift:375-381). Users can't tell why a scan failed.
**G12 · "Clear All History…" wipes immediately** — no confirmation dialog (SettingsScreen.swift:139-142); the "…" implies one. Destroys all snapshots + audit log (repeat-offender data) in one click.
**G13 · Duplicates: spec J5 deltas** — no scope selector (scans whole home/scan root) and no keep-newest preselection (selection starts empty; only a count cap enforces keep-one) vs docs/02-ux.md:65.
**G14 · Apps screen "Clean caches" (spec J6) is advice text only** — no action or navigation (AppsScreen.swift:146); J6 promises a "Clean caches" sheet offering the green cache portion.
**G15 · Radar findings have no act-on-finding path** — recommendations are text only (SmartToolsScreens.swift:53-75); several point at screens that can't complete the recommended action (leftovers → G3).
**G16 · Agent tool layer (P7) is an orphan surface** — `ToolRegistry`'s 8 tools incl. `MoveToTrashTool` are invoked only by tests (grep: zero references in Sources/DiskRobo). Foundation by design (docs/07 §P7), but currently unreachable dead weight in the product.
**G17 · External volumes: listed but never scannable** — `VolumeManager` exists and lists browsable volumes (VolumeManager.swift:10-32); no picker; `startScan(roots:)` never receives a volume root; VolumeCard's chevron suggests a menu that doesn't exist (OverviewScreen.swift:78-79). Phase 3 outline acknowledges this — keep as roadmap, but the decorative chevron should go or become real.
**G18 · History/log minor gaps** — cleanup log shows only the last 20 records (HistoryScreen.swift:55-60); `blocked` and `failed` render identically in log rows (HistoryScreen.swift:76-77); duplicate-scan stages (collecting/grouping/hashing/verifying) never surfaced — one spinner text for all; MenuBar has a `.hidden()` dead Cancel button (DiskRoboApp.swift:89-91); RecoverableCard's "Safely cleanable now" is inflated by Trash contents (see G5).

## 6. What this audit is not
